# Note synchronization implementation

Implemented the supplied `NoteSyncService` without changing its public surface, records,
transaction interface, server interface, or dependencies. Local edits atomically save the
note and a new operation with the original version precondition. Failures propagate to the
caller; they do not claim a safe local save or server acknowledgement.

The coordinator scopes reads/delivery to the active account, coalesces repeated sync calls,
and invalidates in-flight completions on logout, account change, and close. Pending and
conflicted records remain in the supplied store. The application must own one active
coordinator per account; there is no cross-instance worker lease in the supplied interface.

Acknowledgements atomically remove only their operation and update known server version,
while preserving the current local body and pending/conflict state of remaining edits.
Conflicts retain the original operation/body/precondition and block automatic replay for
that note. Subsequent edits are retained but remain blocked pending an explicit conflict
resolution workflow. No conflict-resolution API was added. Original preconditions are never
silently rebased, so two edits made from the same version may correctly require resolution.
Other notes can continue syncing after a conflict. A transport or local-store failure ends
that sync attempt; the caller can invoke sync again. No retry timer or scheduler was added.

## Not verified and limits

The store is a transactional in-memory fake retained between coordinator instances. This
proves coordinator policy and fake rollback, not filesystem durability, database adapter
correctness, process-kill recovery, device relaunch, encryption, migrations, or OS scheduling.
The interruption cases model lost delivery/acknowledgement rather than killing a process.
The fake server implements account+operation-ID deduplication and version checks, establishing
one effect under that supplied contract, not a real backend's guarantees. No real credentials
or authentication transport exist in this app; the tests verify account tagging, isolation,
and ignoring stale completion rather than real credential revocation or request cancellation.
Already submitted requests can still reach the server after logout; their local completions
are ignored and retained operations reconcile using server deduplication on a later retry.
There is no device UI, native application target, real database, backend, background worker,
or platform adapter to build or exercise here. No build, device, or backend check is claimed.
