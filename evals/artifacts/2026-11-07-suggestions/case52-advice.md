The [share_plus 12.0.1 documentation](https://pub.dev/packages/share_plus/versions/12.0.1) supports sharing files with text. The [printing API](https://pub.dev/documentation/printing/latest/printing/Printing/sharePdf.html) explicitly limits body/subject to Android and iOS. I would choose printing only for its additional document features, while retaining a separate web sharing approach.

For the first implementation slice, I recommend:

1. Implement `ReportShare` in the reports infrastructure/data layer, provided through Riverpod. Internally use `SharePlus.instance.share` with `ShareParams`: one `XFile.fromData` using MIME `application/pdf`, `fileNameOverrides: [fileName]`, and `text: message`. Validate nonempty bytes and a safe `.pdf` filename first. Keep plugin types inside the adapter. Use the current instance API; older static `Share.share*` methods are deprecated. See the [upstream usage and migration guide](https://raw.githubusercontent.com/fluttercommunity/plus_plugins/main/packages/share_plus/share_plus/README.md).
2. Prepare the bytes before enabling Share; disable repeated taps while the action is pending. The UI owns the tap and geometry. On **iPad**, 12.0.1 requires `sharePositionOrigin` from the visible share button. The current domain signature has no anchor: use an action-scoped adapter/presentation helper supplied with that rectangle, without retaining `BuildContext` in Riverpod state or domain objects. This needs deliberate wiring rather than copying a context-free share call. [Versioned iPad documentation](https://pub.dev/packages/share_plus/versions/12.0.1#ipad).
3. Handle dismissal quietly, map exceptions to a localized retry message, and clear busy state in all outcomes. The current `Future<void>` contract can remain if the UI needs only completion/error. If the UI must distinguish dismissal, download and handoff, introduce an app-owned result type later; do not expose `ShareResult` to domain callers. A share-sheet result is not proof that a recipient received or read the PDF.
4. Define web behavior explicitly: use HTTPS and a direct user gesture; avoid generating/downloading the PDF after the share tap and losing transient activation. Where supported, share the PDF and message together. Otherwise offer **Download PDF** and **Copy message**, explaining that the user must attach/paste them. The built-in file fallback downloads the PDF and does not share the accompanying message. It returns an unavailable result, as does successful browser handoff, so do not infer a download from that status alone. If precise fallback UX matters, disable automatic download fallback and expose the explicit actions. [Versioned web implementation](https://raw.githubusercontent.com/fluttercommunity/plus_plugins/share_plus-v12.0.1/packages/share_plus/share_plus/lib/src/share_plus_web.dart), [Web Share specification](https://w3c.github.io/web-share/).

No package can guarantee every receiving app preserves both file and text, or provide a native share sheet in every browser. If “web sharing” requires guaranteed automated delivery of both everywhere, that needs a different product contract, such as a backend email workflow; downloading is a graceful fallback, not equivalent delivery. Test the actual recipient apps your users need.

For sharing app-owned bytes, I would add no broad storage/photo permission or permission plugin. The Android plugin supplies a FileProvider with temporary URI grants. No sharing backend or signing service is required. Native sharing can start offline, though a receiving app may need connectivity. Sharing byte data creates native cache files: define bounded cleanup of sharing-owned temporary files after they are no longer needed, without deleting unrelated cache data. Do not log report bytes or messages. [Plugin manifest](https://raw.githubusercontent.com/fluttercommunity/plus_plugins/share_plus-v12.0.1/packages/share_plus/share_plus/android/src/main/AndroidManifest.xml), [upstream cache guidance](https://raw.githubusercontent.com/fluttercommunity/plus_plugins/main/packages/share_plus/share_plus/README.md).
