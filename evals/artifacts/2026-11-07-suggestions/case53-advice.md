This recommendation follows the distinction between top-down Pigeon contracts and bottom-up FFIgen/JNIgen bindings in [Flutter’s interop overview](https://docs.flutter.dev/interop). It is an architectural recommendation, not a measured latency result.

Pigeon is a generator, not another name for platform channels. Current documentation also offers a **native FFI/JNI backend in preview**, explicitly unsuitable for stable production use. Select the established channel backend for this app; do not assume the preview is available or compatible with Flutter 3.38.9. The current documentation targets a newer Flutter release. [Pigeon backend documentation](https://docs.flutter.dev/interop/pigeon).

For Swift configuration/events, implement the generated protocol in Swift and call the SDK there. That does not require the vendor to expose Objective-C headers. By contrast, FFIgen’s established Swift route depends on Objective-C-compatible exported APIs; the vendor’s headers are unconfirmed. Pure Swift types or associated-value enums may need a wrapper, and experimental direct Swift tooling is unnecessary for this slice. [FFIgen limitations](https://docs.flutter.dev/interop/ffigen).

The easiest first slice, when implementation is authorized, is:

1. Obtain the exact vendor versions and redistribution/license terms; confirm the required configuration fields, one callback, supported OS/toolchains and the DSP binary matrix. Keep a narrow app-facing capability contract with ordinary Dart values and stable error codes. Use the existing feature data layer and Riverpod composition; generated transport classes, JNI wrappers and pointers stay out of domain/UI.
2. Bridge one configuration call plus one callback on each mobile platform using Pigeon channels. Exercise successful initialization, invalid configuration and listener removal. A callback API mapped to a Dart stream is enough initially; use generated event-stream support only after confirming the chosen generator. Define initial state/replay, order, buffering and unsubscribe behavior. A raw MethodChannel/EventChannel adapter is a reasonable fallback if a very small existing bridge already exists or generator compatibility blocks Pigeon; keep its schema typed at the Dart boundary. [Pigeon 27.3.0 API](https://pub.dev/packages/pigeon/versions/27.3.0).
3. Separately exercise `dsp_create` → one known sample block through `dsp_process` → `dsp_destroy`. Compare output to a vendor-provided golden vector, and cover creation failure, process failure and disposal. Only then connect repeated blocks and measure end-to-end latency, jitter, copying and allocation on representative devices.

The native session owns SDK listeners and resources; its Riverpod provider controls the Dart lifetime and invokes disposal. Choose app/session scope if the session must survive route changes, rather than making a screen own it accidentally. Cancellation must settle outstanding requests once and discard late callbacks. Native teardown removes observers and listeners before releasing their targets; Android Activity detach/reattach and iOS foreground/background need explicit behavior. Keep denied permissions, unsupported capability, cancellation and vendor errors distinct where applicable. Do not add permissions without identifying the actual SDK requirement.

The DSP header exposes an opaque `DspContext`, C `int`/`size_t`, and input/output `float*` arrays. Bind the actual ABI types, not guessed integer widths. Confirm whether length means samples or frames, channel layout, output capacity, allowed in-place processing, error-code semantics, buffer alignment, whether pointers are retained, and context thread safety. None is established by the header. Check null creation before use. The adapter allocates and reuses suitably sized native buffers, frees them through the matching allocator and destroys the context exactly once after all processing has finished. Never use a context after disposal.

A synchronous FFI call can block the UI isolate. For ordinary chunked processing, a long-lived worker isolate can own its context and buffers, subject to vendor thread requirements; `async` alone does not move work. Include isolate messaging/copies in measurements. If this is a hard real-time audio callback, keep the deadline-sensitive processing and buffering on the vendor/native audio thread and send only control/status to Dart. Dart scheduling is not a real-time guarantee. Avoid marking a potentially long DSP call as a leaf call merely to seek speed. [Dart C interop](https://dart.dev/interop/c-interop).
